## 2. 业务需求说明 (PRD)

### 业务背景
星辰数科知识库涵盖研发、HR、财务、法务四个部门的内部文档，需要支持按语义相似度毫秒级召回，并严格支持按部门（`dept`）或文档类型（`doc_type`）进行权限与范围过滤。

### 核心痛点
- 纯关键字 SQL `LIKE '%报销%'` 查不到「差旅住宿补贴标准」这类语义相近但字面不同的文档。
- 文档全量暴力遍历在大规模语料下性能下降明显，需要理解并引入 ANN/HNSW 索引机制。
- 不同部门员工只能检索本部门公开文档，向量检索必须结合元数据 `where` 条件过滤。

### 迭代目标
- 实现确定性中文稠密向量化模型（归一化余弦空间，兼容 `bge-large-zh-v1.5` 接口协议）。
- 实现教学级 HNSW 分层近邻图索引，直观验证分层跳转搜索过程。
- 实现类 Chroma 风格本地持久化向量库 `StarMindVectorStore`，支持 `add_documents`、`similarity_search_with_score`、`where` 元数据过滤及磁盘保存/加载。

### 验收标准
- [x] 语义相近的查询（如「出差住酒店上限」与「一线城市住宿标准600元」）能稳居 Top-1 召回。
- [x] 传入 `where={'dept': '研发部'}` 时，返回结果 100% 仅来自研发部文档。
- [x] 执行 `persist()` 落盘后，重新实例化 `StarMindVectorStore` 可完整恢复所有向量与文档，pytest 100% 通过。

### 非功能指标
- 所有向量经过 L2 归一化，余弦相似度等价于高效点积运算。
- 持久化格式清晰可读（JSON/SQLite），无 C++ 编译环境依赖。

## 3. 架构设计与交付清单

企业级向量检索架构选型需要综合考量「数据规模、过滤复杂度、运维人力、数据合规」四个维度：
- **FAISS**（Meta 开源）：本质是 C++ 向量索引库（不是完整数据库），没有原生 CRUD、没有元数据过滤、没有分布式高可用，适合算法离线评测或百万级以下只读静态库。
- **Chroma**：极简 Python 优先的嵌入式向量库，开箱即用、支持本地持久化与元数据过滤，非常适合 10 万条以内的原型验证与中小团队单机部署。
- **Milvus / Qdrant / pgvector**：生产级企业首选。如果公司已有 PostgreSQL 团队且向量在 500 万以内，直接开 `pgvector` 插件（省去一套数据库运维，还能跟业务表做 ACID 事务 JOIN）；如果数据量破千万且需要高并发分布式集群，国产之光 **Milvus** 或 Rust 写的 **Qdrant** 是不二之选。
- **Pinecone**：全托管 SaaS，省心但数据出境受限，国内政企和金融客户一般无法使用。

在索引层面，**HNSW（Hierarchical Navigable Small World）** 已成为工业界事实标准：它在建索引时以指数衰减概率将节点随机分配到不同层级，顶层稀疏做长距离粗定位，底层稠密做精细近邻搜索，实现了 $O(\log N)$ 级别的查询复杂度与 95%+ 的高召回率。
