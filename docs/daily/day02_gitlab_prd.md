## 2. 业务需求说明 (PRD)

### 业务背景
客服系统每天产生数万条用户反馈文本，直接送入大模型分析会导致 Token 浪费高达 25%，且格式杂乱影响模型抽取准确度。

### 核心痛点
- 用户输入包含大量多余空白、制表符、全角空格及无意义重复标点。
- 客服提问缺少统一上下文结构，直接丢给大模型经常答非所问。
- 缺乏快速预估文本长度与是否超限的规则判断。

### 迭代目标
- 掌握算术、比较、逻辑与成员运算符（in / not in）及短路求值特性。
- 熟练运用字符串切片、strip/replace/split/join/lower/upper 等核心方法。
- 使用 f-string 构建结构化 Prompt 模板，并实现可复用的文本清洗函数。

### 验收标准
- [x] 文本清洗器能清除首尾空白、折叠连续空格、统一全角空格并标准化订单号前缀。
- [x] Prompt 模板能动态注入角色、用户问题、字数限制并计算估算 Token 数。
- [x] 所有边界用例（空字符串、超长文本截断、敏感词命中检测）通过 pytest。

### 非功能指标
- 纯字符串方法实现，单条清洗耗时低于 1ms。
- 遵循纯函数设计，不修改外部状态。

## 3. 架构设计与交付清单

在星辰智脑的文本预处理链路中，我们采用「管道式（Pipeline）清洗架构」：
原始脏文本 -> 全角/特殊空白归一化 -> 连续空白折叠 -> 订单号标准化 -> 长度合规截断 -> 注入 Prompt 模板。
为什么要把清洗和模板渲染拆成两个独立模块（day02_text_cleaner.py 与 day02_prompt_template.py）？
因为清洗器是全平台通用的基础组件（后续 RAG 文档切片、日志分析都要复用），而 Prompt 模板强绑定业务场景（客服、摘要、翻译各有各的模板）。这种按「变化频率」拆分模块的思路，是大厂架构师最常用的解耦手法。

### 当日交付代码文件

- `src/day02_prompt_template.py`：步骤二：打造 f-string Prompt 模板渲染与 Token 估算引擎
