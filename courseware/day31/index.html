3. 架构设计与矢量工程图谱（流程图 / 架构图 / 原理示意图）

3.1 架构设计思路与技术选型权衡

在企业级 RAG 研发流程中，**「先建评估基线，再做优化迭代」**是铁律。今天我们引入信息检索（IR）领域最经典的两个量化指标来衡量检索器（Retriever）的好坏：
1. **Hit Rate @ K（Top-K 命中率）**：对于测试集中的 $N$ 个问题，只要正确参考文档出现在检索返回的前 $K$ 条结果中就记为 1，否则为 0：
$$\text{Hit@K} = \frac{1}{N} \sum_{i=1}^{N} \mathbb{I}(\text{gold}_i \in \text{TopK}_i)$$
2. **MRR（Mean Reciprocal Rank，平均倒数排名）**：不仅看有没有命中，还看排在第几位！排第 1 得 $1.0$ 分，排第 2 得 $0.5$ 分，排第 3 得 $0.333$ 分，未命中得 $0$ 分：
$$\text{MRR} = \frac{1}{N} \sum_{i=1}^{N} \frac{1}{\text{rank}_i}$$

在消融实验中，我们严格遵循「控制变量法」，将语料库和黄金评测集固定，系统性地扫描 (chunk_size, chunk_overlap, top_k, embedding_mode) 四维参数空间，把每一次实验的 Hit@K、MRR、Chunks 数量和 Avg Latency 全部打成结构化表格，从而科学选出最优线上配置。

4. 课堂核心技术笔记与深度原理解析

1. 1. 为什么检索调优不能只看 Hit@K，必须配合 MRR？

假设你把 top_k 设成 10，Hit@10 很容易飙到 98%，看起来很美；但如果正确答案排在第 8 位，喂给大模型时不仅白白多花 7 个噪音切片的 Token 钱，还极易触发大模型的「Lost in the Middle（中间信息遗忘）」现象！而 **MRR** 强迫优化目标把正确答案推到第 1、第 2 位，才是真正有工程意义的指标。

⚠️ 老陈避坑提示：踩坑提醒：切忌把测试集里的原句直接拿来做评测！真实员工提问往往是口语化、错别字或同义词改写，黄金评测集必须包含至少 50% 的「换种说法提问」样本。

2. 2. Embedding 模型横评维度（国内企业落地指南）

在生产环境选型 Embedding 模型时，除了看 MTEB 中文榜单（C-MTEB），更要关注 4 个工程指标：
1. **向量维度**：bge-small-zh（512 维）存储和检索成本只有 bge-large-zh（1024 维）的一半，中小知识库差距不到 2%；
2. **最大输入长度**：bge-large-zh-v1.5 仅支持 512 Token（超长直接截断！），而 BGE-M3 支持 8192 Token；
3. **查询前缀指令**：部分 BGE 模型要求对 Query 加指令前缀 '为这个句子生成表示以用于检索相关文章：'，文档侧不加；
4. **推理延迟与显存**：在无 GPU 的普通 CPU 服务器上，优先选 ONNX 量化版 bge-small-zh 或直接调阿里云 text-embedding-v3。

⚠️ 老陈避坑提示：踩坑提醒：千万别把 `chunk_size` 设成 1000 字却配一个最大只支持 512 Token 的 Embedding 模型！后 500 字会被静默截断，永远检索不到！

    """弱基线 Embedding（仅用单字特征、无双字词组与同义词槽），用于消融对比。"""

    def __init__(self, dim: int = 64) -> None:
        super().__init__(dim=dim)

    def _extract_features(self, text: str) -> List[Tuple[str, float]]:
        return [(f"c1:{ch}", 1.0) for ch in re.findall(r"[\u4e00-\u9fff]", text)]

def load_base_corpus() -> List[Document]:
    loader = MarkdownLoader()
    docs: List[Document] = []
    for filename, dept, md_text in STARMIND_CORPUS:
        parsed = loader.load_text(md_text, source=filename)
        for d in parsed:
            d.metadata["dept"] = dept
        docs.extend(parsed)
    return docs


def evaluate_config(
    exp_name: str,
    embedding_name: str,
    embeddings: StarMindLocalEmbeddings,
    chunk_size: int,
    chunk_overlap: int,
    top_k: int,
    eval_set: Sequence[EvalCase] = GOLDEN_EVAL_SET,
) -> ExperimentResult:
    """运行单组超参数配置，返回 Hit@K、MRR 与平均检索延迟。"""
    base_docs = load_base_corpus()
    chunks = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size, chunk_overlap=chunk_overlap
    ).split_documents(base_docs)

    store = StarMindVectorStore(collection_name=f"ablation_{exp_name}", embedding_function=embeddings)
    store.add_documents(chunks)

    hits = 0
    rr_sum = 0.0
    total_ms = 0.0

    for case in eval_set:
        t0 = time.perf_counter()
        results = store.similarity_search(case.question, k=top_k)
        total_ms += (time.perf_counter() - t0) * 1000

        found_rank = 0
        for rank, doc in enumerate(results, start=1):
            if doc.metadata.get("source") == case.expected_source and case.expected_keyword in doc.page_content:
                found_rank = rank
                break
        if found_rank > 0:
            hits += 1
            rr_sum += 1.0 / found_rank

    n = max(1, len(eval_set))
    return ExperimentResult(
        exp_name=exp_name,
        embedding_name=embedding_name,
        chunk_size=chunk_size,
        top_k=top_k,
        num_chunks=len(chunks),
        hit_at_k=round(hits / n, 4),
        mrr=round(rr_sum / n, 4),
        avg_latency_ms=round(total_ms / n, 3),
    )


def run_ablation_suite() -> List[ExperimentResult]:
    """执行 6 组控制变量消融实验。"""
    configs = [
        ("E1_基线单字_64d", "Char-64d", BaselineCharEmbeddings(dim=64), 160, 20, 3),
        ("E2_小切片_60字", "StarMind-256d", StarMindLocalEmbeddings(dim=256), 60, 10, 3),
        ("E3_中切片_140字", "StarMind-256d", StarMindLocalEmbeddings(dim=256), 140, 20, 3),
        ("E4_大切片_260字", "StarMind-256d", StarMindLocalEmbeddings(dim=256), 260, 30, 3),
        ("E5_中切片_Top1", "StarMind-256d", StarMindLocalEmbeddings(dim=256), 140, 20, 1),
        ("E6_中切片_Top5", "StarMind-256d", StarMindLocalEmbeddings(dim=256), 140, 20, 5),
    ]
    return [evaluate_config(*cfg) for cfg in configs]


def render_markdown_report(results: Sequence[ExperimentResult]) -> str:
    lines = [
        "| 实验组 | Embedding模型 | ChunkSize | TopK | 切片数 | Hit@K | MRR | 平均耗时(ms) |",
        "|---|---|---:|---:|---:|---:|---:|---:|",
    ]
    for r in results:
        lines.append(
            f"| {r.exp_name} | {r.embedding_name} | {r.chunk_size} | {r.top_k} | "
            f"{r.num_chunks} | {r.hit_at_k:.2%} | {r.mrr:.3f} | {r.avg_latency_ms:.3f} |"
        )
    best = max(results, key=lambda x: (x.mrr, x.hit_at_k, -x.avg_latency_ms))
    lines.append(f"\n推荐线上配置：**{best.exp_name}**（MRR={best.mrr:.3f}, Hit@K={best.hit_at_k:.2%}）")
    return "\n".join(lines)

很多零基础转行或者刚毕业的同学进公司后，最容易踩的第一个坑不是代码写不出来，而是“需求没听懂就开始埋头写代码”，写完三天提测才发现跟产品经理要的南辕北辙。今天我们以 STARMIND-031（周测 + RAG效果调优实验日：核心考点实战与多维消融基准报告）为例，把星辰数科每周一上午需求评审会的真实对话逻辑拆开揉碎了讲给你听。业务背景非常明确：星辰智脑知识库 V1.0 准备向全员开放，但在全量发布前需要通过研发周测验收，并给出一份基于黄金测试集的 RAG 超参数调优基准报告（确定线上默认的 chunk_size、top_k 与 Embedding 策略）。 在评审会上，林产品抛出来的核心业务痛点集中在：（1）团队成员对 LCEL、Memory 隔离与 RAG 边界条件掌握参差不齐，需要自动化周测检验。；（2）RAG 超参数（chunk_size / overlap / top_k / embedding）长期靠拍脑袋设定，缺乏量化指标支撑。；（3）每次改完检索策略靠人工肉眼测两三个问题，容易「修好一个 Case、弄坏十个 Case」。。如果你只盯着字面意思去写一个“一次性脚本”，短期看似交付很快，但两周后业务方加一个新字段、换一个大模型厂商或者并发量翻倍时，整段代码就得推倒重来。

老陈在评审会上通常只追问三个致命问题，建议你拿小本本记下来，以后带项目直接套用：第一问“输入数据的最坏情况长什么样？”——比如用户会不会粘进来 5 万字乱码、空文件、或者带 SQL 注入/提示词注入的恶意文本；第二问“业务方能接受的失败兜底策略是什么？”——在大模型应用里，100% 不出错是不可能的，关键是出错时系统是直接 500 白屏，还是友好提示、自动降级并留存日志；第三问“哪些指标能证明我们今天这版上线是成功的？”——围绕今天定下的交付目标：（1）构建覆盖 Day 25~30 五大核心考点的自动化编程周测评测器并 100% 通关。；（2）实现检索核心评估指标：Hit@K（命中率）、MRR（平均倒数排名）与平均检索延迟。；（3）构建多组超参数网格消融实验引擎（chunk_size x top_k x embedding_mode），自动产出量化对比表与最优配置推荐。，必须全部翻译成可量化的测试用例和监控指标（例如 Top-5 召回率 >= 90%，忠实度 Faithfulness >= 0.88，所有回答必须附带可溯源引用锚点）。

经过这三轮对齐，我们在飞书需求文档里落定了今天的技术边界：明确哪些能力放在当天版本 versions/day31/ 里做透做稳，哪些属于过度设计（Over-engineering）暂时留好接口扩展位而不急着实现。记住国内互联网大厂一条铁律：好的架构不是一开始就画一张大而全的宇航级图纸，而是像今天这样，在清晰抽象边界的前提下，让每一个迭代版本都能独立跑通、独立测试、独立交付业务价值。

实战方法论三：从“能跑就行”到“生产级代码”——Day 31 模块的代码品味与重构准则

今天我们在 versions/day31/ 中亲手编写了 src/day31_weekly_quiz.py、src/day31_rag_ablation.py 以及对应的自动化测试 tests/test_day31.py。站在初级开发者视角，代码只要在控制台打印出预期结果就算大功告成；但站在星辰数科技术委员会的 Code Review 视角，一段代码能不能合入主干，要过四道硬核关卡：第一关是“单一职责与低耦合”——函数长度尽量控制在 40~60 行以内，如果一个函数既负责读取配置、又负责清洗文本、还负责调接口和写文件，那它一定难以复用和单测；第二关是“命名即文档”——变量名绝不用 a、b、data1、temp2，而是直接用业务含义命名（如 sanitized_prompt、chunk_overlap、trace_id），配合 Python 类型注解（Type Hints），让阅读者一眼看清数据契约；第三关是“显式错误处理”——绝不写光秃秃的 except: pass 吞掉异常，因为吞掉异常等于在生产环境埋下一颗定时炸弹，真出故障时连日志都查不到；第四关是“可测试性”——任何涉及外部网络、系统时间、随机数或付费大模型 API 的逻辑，都要支持通过依赖注入或 local_mock 切换在离线环境 100% 确定性地跑通回归测试。

对照这四道关卡回头审视你今天写下的每一行代码，你会清晰感受到：大模型应用开发绝不是“调个 API 写两句提示词”那么肤浅的玩具活，它本质上是“扎实的软件工程底座 + 大模型概率特性治理 + 垂直业务场景洞察”的三位一体。国内企业现在最缺、薪资给得最高的，恰恰是既懂 Python/FastAPI/Docker 工程落地，又懂 RAG/Agent/微调底层调优的复合型 AI 应用工程师。

9. 生产环境排障实录与工程验收自查表

故障演练一：周测 + RAG效果调优实验日：核心考点实战与多维消融基准报告 核心链路在异常脏数据或边界输入下触发未预期中断

【线上现象】在联调 STARMIND-031 对应的功能模块时，开发机上用自己构造的“干净样例”跑得丝滑无比，但一交给阿杰跑边界测试（如空文本、超长中文混排、包含特殊 Emoji 或嵌套缺失字段的 JSON），控制台直接抛出未捕获异常，导致整个服务进程或上游调用链雪崩。

【根因定位】根本原因在于把“理想假设”当成了“生产契约”。在 LCEL 可组合管道、多会话记忆隔离、中文递归分块、向量数据库与 HNSW 近似检索、BM25+向量混合检索、RRF 融合、Rerank 重排与 Ragas 量化评估 环节，上游业务系统传过来的数据往往充满历史包袱（比如字段值为 None 而非空字符串、编码混杂 GBK/UTF-8、或者模型偶发少输出一个右括号）。如果函数入口缺少显式的参数防御与 Pydantic/类型校验，异常就会在深层调用栈里爆炸。

【止血与根治方案】

1. 在所有对外暴露的入口函数与接口层建立“防御性边界”，先校验、清洗并标准化输入，再进入核心逻辑；
2. 为当日核心模块补充至少 3 组异常/空值/极值单元测试，并纳入 tests/test_day31.py 回归集合；
3. 捕获可预期异常时，返回结构化错误对象并附带 trace_id，方便在飞书告警群里一眼定位到具体是哪条请求出了岔子。

故障演练二：性能退化、成本突增与线上可观测性盲区（切片过大稀释语义/过小截断上下文、召回率不足引发大模型幻觉、跨租户知识库越权检索）

【线上现象】上线试运行两天后，林产品反馈早高峰时段页面转圈变慢，同时财务侧看到大模型 API 账单曲线出现异常毛刺，但翻开服务器日志却只看到零星几句 `print('ok')`，完全无法还原当时到底哪个环节耗时最长、哪条 Prompt 吃掉了最多 Token。

【根因定位】缺少工程化的日志分级、耗时打点与配额熔断机制。很多从零基础转行过来的同学习惯用 `print` 调试完就留在线上，既没有时间戳和请求追踪号，也没有统计输入/输出 Token 数和单步耗时；一旦外部接口抖动或触发死循环重试，成本就会在几分钟内失控。

【止血与根治方案】

1. 严格使用标准 logging 模块替代裸 print，记录关键节点的入参摘要、耗时毫秒数（latency_ms）和状态码；
2. 针对所有外部 I/O（文件、数据库、HTTP/LLM API）显式设置 timeout 超时上限和最大重试次数（通常 <= 3 次 + 指数退避）；
3. 定期对照今日 SLA 基线（Top-5 召回率 >= 90%，忠实度 Faithfulness >= 0.88，所有回答必须附带可溯源引用锚点）跑压测回归，把隐性瓶颈消灭在灰度发布之前。

故障演练三：国内团队跨环境一致性问题（开发环境能跑，测试/Docker 环境报错）

【线上现象】学员在自己 Windows/Mac 笔记本的 VS Code 里运行 Day 31 代码一切正常，但提交到 GitLab CI（Linux Debian 容器环境）后，出现文件路径分隔符报错、时区偏差或国内网络下载依赖超时。

【根因定位】代码中硬编码了反斜杠路径（如 `data\test.json`）或绝对路径（如 `C:\Users\...`），未统一使用 `pathlib.Path`；同时 `pip install` 未指定国内镜像源或 `requirements.txt` 未锁定主版本号。

【止血与根治方案】

1. 全仓库统一使用 pathlib.Path(__file__).resolve().parent 构建相对路径，彻底告别跨平台路径坑；
2. 打开文本文件强制显式传参 encoding='utf-8'，避免 Windows 默认 GBK 编码引发的 UnicodeDecodeError；
3. 依赖安装统一配置清华源 -i https://pypi.tuna.tsinghua.edu.cn/simple，并在 README.md 中固定 Python 3.11+ 版本要求。

作业 1：作业一：实现 NDCG@K（归一化折损累计增益）检索评估指标基础巩固

当一个问题需要多篇文档共同支撑（例如既需要「住宿标准」又需要「餐补标准」）时，MRR 只看第一篇命中文档不够全面。请实现 compute_ndcg(relevances, k)：输入检索返回前 K 条文档的相关度列表（如 [1, 0, 1]），计算并返回 $\text{NDCG@K} = \text{DCG@K} / \text{IDCG@K}$。

💡 思路提示：$\text{DCG@K} = \sum_{i=1}^{K} \frac{rel_i}{\log_2(i + 1)}$，IDCG 是将 `relevances` 降序排列后的理想 DCG。

✅ 参考实现代码（作业 1）
"""Day 31 作业一参考答案：多相关文档评估指标 NDCG@K"""
import math
from typing import Sequence


def compute_dcg(relevances: Sequence[float], k: int) -> float:
    return sum(rel / math.log2(idx + 2) for idx, rel in enumerate(relevances[:k]))


def compute_ndcg(relevances: Sequence[float], k: int) -> float:
    actual = compute_dcg(relevances, k)
    ideal = compute_dcg(sorted(relevances, reverse=True), k)
    return round(actual / ideal, 4) if ideal > 0 else 0.0


if __name__ == "__main__":
    print("理想排序 [1, 1, 0] -> NDCG@3 =", compute_ndcg([1, 1, 0], 3))
    print("次优排序 [0, 1, 1] -> NDCG@3 =", compute_ndcg([0, 1, 1], 3))
    assert compute_ndcg([1, 1, 0], 3) == 1.0
    assert compute_ndcg([0, 1, 1], 3) < 1.0

"""Day 31 作业三参考答案：防幻觉拒答阈值自动标定器"""
import sys
from pathlib import Path
from typing import List, Tuple

ROOT = Path(__file__).resolve().parents[1]
if str(ROOT) not in sys.path:
    sys.path.insert(0, str(ROOT))

from src.day30_kb_cli import build_starmind_kb


def calibrate_threshold(
    positive_queries: List[str],
    negative_queries: List[str],
    candidates: List[float],
) -> Tuple[float, float]:
    kb = build_starmind_kb()
    pos_scores = [
        (kb.vector_store.similarity_search_with_score(q, k=1) or [(None, 0.0)])[0][1]
        for q in positive_queries
    ]
    neg_scores = [
        (kb.vector_store.similarity_search_with_score(q, k=1) or [(None, 0.0)])[0][1]
        for q in negative_queries
    ]

    best_th, best_f1 = candidates[0], -1.0
    for th in candidates:
        tp = sum(1 for s in pos_scores if s >= th)
        tn = sum(1 for s in neg_scores if s < th)
        recall = tp / max(1, len(pos_scores))
        spec = tn / max(1, len(neg_scores))
        f1 = (2 * recall * spec / (recall + spec)) if (recall + spec) > 0 else 0.0
        print(f"threshold={th:.2f} | 库内召回={recall:.2%} | 库外拒答={spec:.2%} | 综合F1={f1:.3f}")
        if f1 > best_f1:
            best_f1, best_th = f1, th
    return best_th, best_f1


if __name__ == "__main__":
    pos = ["北京出差住宿报销上限", "年假需要提前几天申请", "周五晚上可以发布代码吗"]
    neg = ["火星大气层成分", "红烧肉怎么做最好吃", "世界杯冠军是哪支球队"]
    th, f1 = calibrate_threshold(pos, neg, [0.10, 0.15, 0.20, 0.25, 0.30, 0.35])
