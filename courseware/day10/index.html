4. 课堂核心技术笔记与深度原理解析

1. 1. 模块、包与 __name__ == '__main__'

一个 .py 文件就是一个模块（Module）；包含 __init__.py 的文件夹就是一个包（Package）。每个模块都应把演示代码放进 if __name__ == '__main__': 块里，否则别人 import 你的模块时会意外执行你的演示打印甚至触发网络请求！

⚠️ 老陈避坑提示：切忌把自己的业务文件命名为 `json.py`、`random.py` 或 `requests.py`！那会遮蔽（Shadow）同名标准库或第三方库，引发极其诡异的 `AttributeError`。

2. 2. try / except / else / finally 完整语义

- try：放可能出错的最小范围代码；
- except SpecificError as e：精准捕获并处理；
- else：仅当 try 块**完全没有异常**时执行；
- finally：**无论是否发生异常（甚至有 return）**都必然执行，用来关闭文件、释放锁、记录审计日志。

⚠️ 老陈避坑提示：重新包装异常时务必使用 `raise StarMindError('调用失败') from orig_exc`，这样 traceback 会保留原始报错链，排查效率翻倍。

3. 3. venv 虚拟环境与 requirements.txt

标准三步：python3 -m venv .venv 创建隔离环境 -> 激活后安装依赖 -> pip freeze > requirements.txt 锁定版本。团队新人拉下代码后只需 pip install -r requirements.txt 即可 100% 复现一致环境。

⚠️ 老陈避坑提示：千万别在 `requirements.txt` 里只写包名不锁版本（如只写 `pydantic`），某天上游发了个不兼容大版本，你的线上镜像一重新构建直接挂掉！

深度拓展：生产级底层原理与国内团队落地经验谈

【生产血泪教训：循环导入（Circular Import）怎么破？】
项目文件一多，经常出现 a.py import b.py，b.py 又 import a.py，一运行直接 ImportError: cannot import name ... from partially initialized module。
大厂根治三板斧：1）把公共类型、常量、异常抽到最底层独立的 exceptions.py / schemas.py；2）保证模块依赖是单向有向无环图（DAG）；3）仅做类型标注时用 if TYPE_CHECKING: 延迟导入。

"""
STARMIND-010 模块一：星辰智脑自定义异常体系。
演示异常类继承、结构化错误元数据（code/retryable）以及标准错误字典序列化。
"""

from typing import Dict, Any


class StarMindError(Exception):
    """星辰智脑平台所有业务异常的统一基类。"""

    code: str = "E500"
    retryable: bool = False

    def __init__(self, message: str, detail: str = "") -> None:
        super().__init__(message)
        self.message = message
        self.detail = detail

    def to_error_dict(self) -> Dict[str, Any]:
        """将异常转为前后端统一的 JSON 错误响应结构。"""
        return {
            "ok": False,
            "error_code": self.code,
            "message": self.message,
            "detail": self.detail,
            "retryable": self.retryable,
        }


class RateLimitError(StarMindError):
    """上游大模型触发限流（HTTP 429），支持退避重试或切备用模型。"""

    code = "E429"
    retryable = True


class ModelTimeoutError(StarMindError):
    """上游大模型推理超时（HTTP 504），支持降级重试。"""

    code = "E504"
    retryable = True


class AuthError(StarMindError):
    """API Key 无效或已过期（HTTP 401），不可重试，需立即告警人工介入。"""

    code = "E401"
    retryable = False


if __name__ == "__main__":
    err = RateLimitError("DeepSeek 主通道触发 TPM 限流", detail="retry-after: 3s")
    print("异常字典:", err.to_error_dict())
# 预期运行输出示例： 异常字典: {'ok': False, 'error_code': 'E429', 'message': 'DeepSeek 主通道触发 TPM 限流', 'detail': 'retry-after: 3s', 'retryable': True}

"""
STARMIND-010 模块二：主备模型容错执行器与 requirements.txt 规范审计工具。
演示 try/except/else/finally、精准异常分流、异常链 raise...from 与工程依赖检查。
"""

from typing import Callable, Dict, Any, List
from day10_exceptions import StarMindError, AuthError


def call_with_fallback(
    primary_fn: Callable[[str], str],
    fallback_fn: Callable[[str], str],
    prompt: str,
) -> Dict[str, Any]:
    """
    高可用模型调用调度器：
    - 主模型正常：直接返回 primary 结果；
    - 主模型抛出可重试 StarMindError（如 RateLimitError/Timeout）：自动降级至备用模型；
    - 主模型抛出 AuthError 等不可重试异常：立即透传上抛，绝不掩盖根因。
    """
    audit_events: List[str] = []
    try:
        audit_events.append("try_primary")
        reply = primary_fn(prompt)
    except AuthError:
        # 鉴权失败属于配置事故，不降级直接暴露
        audit_events.append("auth_abort")
        raise
    except StarMindError as exc:
        if not exc.retryable:
            audit_events.append("non_retryable_abort")
            raise
        # 可重试/可降级异常：自动切换备用模型
        audit_events.append(f"fallback_on_{exc.code}")
        try:
            reply = fallback_fn(prompt)
            channel = "fallback"
        except Exception as fb_exc:
            raise StarMindError("主备模型均调用失败", detail=str(fb_exc)) from fb_exc
    else:
        # 仅当 try 块完全无异常时执行
        channel = "primary"
        audit_events.append("primary_ok")
    finally:
        # 无论成功、降级还是抛异常，审计收尾钩子必然执行
        audit_events.append("audit_closed")

    return {
        "ok": True,
        "channel": channel,
        "reply": reply,
        "audit_events": audit_events,
    }


def audit_requirements_text(req_content: str) -> Dict[str, List[str]]:
    """检查 requirements.txt 文本，识别已锁版本与未锁版本的风险依赖。"""
    pinned: List[str] = []
    unpinned: List[str] = []
    for raw_line in req_content.splitlines():
        line = raw_line.strip()
        if not line or line.startswith("#"):
            continue
        if "==" in line:
            pinned.append(line)
        else:
            unpinned.append(line)
    return {"pinned": pinned, "unpinned": unpinned}


if __name__ == "__main__":
    from day10_exceptions import RateLimitError

    def mock_primary(_p: str) -> str:
        raise RateLimitError("主通道 429 限流")

    def mock_fallback(p: str) -> str:
        return f"[备用通义千问兜底] 已处理: {p}"

    print("降级结果:", call_with_fallback(mock_primary, mock_fallback, "查询报销流程"))
    sample_req = "# 核心依赖\nfastapi==0.115.0\npydantic\nuvicorn==0.30.0\n"
    print("依赖审计:", audit_requirements_text(sample_req))
# 预期运行输出示例： 降级结果: {'ok': True, 'channel': 'fallback', 'reply': '[备用通义千问兜底] 已处理: 查询报销流程', 'audit_events': ['try_primary', 'fallback_on_E429', 'audit_closed']} 依赖审计: {'pinned': ['fastapi==0.115.0', 'uvicorn==0.30.0'], 'unpinned': ['pydantic']}

很多零基础转行或者刚毕业的同学进公司后，最容易踩的第一个坑不是代码写不出来，而是“需求没听懂就开始埋头写代码”，写完三天提测才发现跟产品经理要的南辕北辙。今天我们以 STARMIND-010（模块、包与异常处理）为例，把星辰数科每周一上午需求评审会的真实对话逻辑拆开揉碎了讲给你听。业务背景非常明确：星辰智脑接入多模型后，生产环境频繁面临上游 429 限流、401 密钥失效、输入超长等故障，需要统一的自定义异常体系、优雅降级机制与标准化依赖隔离方案。 在评审会上，林产品抛出来的核心业务痛点集中在：（1）所有错误都抛出泛化的 Exception，调用方无法区分该重试、该切模型还是该立即报警。；（2）裸 except Exception: pass 掩盖了真实故障根因。；（3）团队成员全局 pip 装包互相打架，缺少 venv 与 requirements.txt 规范检查。。如果你只盯着字面意思去写一个“一次性脚本”，短期看似交付很快，但两周后业务方加一个新字段、换一个大模型厂商或者并发量翻倍时，整段代码就得推倒重来。

【核心专题 1 深度复盘：1. 模块、包与 __name__ == '__main__'】课堂上我们梳理了主干原理，但在企业真实开发里，决定代码上限的往往是对细节和反例的拿捏。回顾本节关键脉络：一个 .py 文件就是一个模块（Module）；包含 __init__.py 的文件夹就是一个包（Package）。每个模块都应把演示代码放进 if __name__ == '__main__': 块里，否则别人 import 你的模块时会意外执行你的演示打印甚至触发网络请求！…… 许多同学在自学这一块时容易陷入“只看 Demo 成功路径”的误区，以为把官方文档里的 10 行示例代码跑出结果就算掌握了。实际上，真正上线踩坑的 80% 都集中在刚才反复敲黑板的盲区里：切忌把自己的业务文件命名为 json.py、random.py 或 requests.py！那会遮蔽（Shadow）同名标准库或第三方库，引发极其诡异的 AttributeError。。老陈建议你在做完今天的 Notebook 实操后，刻意做一次“破坏性实验”：把输入参数改成非法类型、把配置项删掉一个字段、把数据量放大 100 倍，观察程序的内存占用、执行耗时和报错堆栈。只有亲手把一个模块“搞崩”再亲手修好，你对「1. 模块、包与 __name__ == '__main__'」的理解才算真正刻进了肌肉记忆。

实战方法论三：从“能跑就行”到“生产级代码”——Day 10 模块的代码品味与重构准则

今天我们在 versions/day10/ 中亲手编写了 src/day10_exceptions.py、src/day10_resilient_runner.py 以及对应的自动化测试 tests/test_day10.py。站在初级开发者视角，代码只要在控制台打印出预期结果就算大功告成；但站在星辰数科技术委员会的 Code Review 视角，一段代码能不能合入主干，要过四道硬核关卡：第一关是“单一职责与低耦合”——函数长度尽量控制在 40~60 行以内，如果一个函数既负责读取配置、又负责清洗文本、还负责调接口和写文件，那它一定难以复用和单测；第二关是“命名即文档”——变量名绝不用 a、b、data1、temp2，而是直接用业务含义命名（如 sanitized_prompt、chunk_overlap、trace_id），配合 Python 类型注解（Type Hints），让阅读者一眼看清数据契约；第三关是“显式错误处理”——绝不写光秃秃的 except: pass 吞掉异常，因为吞掉异常等于在生产环境埋下一颗定时炸弹，真出故障时连日志都查不到；第四关是“可测试性”——任何涉及外部网络、系统时间、随机数或付费大模型 API 的逻辑，都要支持通过依赖注入或 local_mock 切换在离线环境 100% 确定性地跑通回归测试。

对照这四道关卡回头审视你今天写下的每一行代码，你会清晰感受到：大模型应用开发绝不是“调个 API 写两句提示词”那么肤浅的玩具活，它本质上是“扎实的软件工程底座 + 大模型概率特性治理 + 垂直业务场景洞察”的三位一体。国内企业现在最缺、薪资给得最高的，恰恰是既懂 Python/FastAPI/Docker 工程落地，又懂 RAG/Agent/微调底层调优的复合型 AI 应用工程师。

9. 生产环境排障实录与工程验收自查表

故障演练一：模块、包与异常处理 核心链路在异常脏数据或边界输入下触发未预期中断

【线上现象】在联调 STARMIND-010 对应的功能模块时，开发机上用自己构造的“干净样例”跑得丝滑无比，但一交给阿杰跑边界测试（如空文本、超长中文混排、包含特殊 Emoji 或嵌套缺失字段的 JSON），控制台直接抛出未捕获异常，导致整个服务进程或上游调用链雪崩。

【根因定位】根本原因在于把“理想假设”当成了“生产契约”。在 Python 工程地基、数据结构与类型安全、JSON 协议解析、面向对象抽象、异步与 HTTP 接口调用 环节，上游业务系统传过来的数据往往充满历史包袱（比如字段值为 None 而非空字符串、编码混杂 GBK/UTF-8、或者模型偶发少输出一个右括号）。如果函数入口缺少显式的参数防御与 Pydantic/类型校验，异常就会在深层调用栈里爆炸。

【止血与根治方案】

1. 在所有对外暴露的入口函数与接口层建立“防御性边界”，先校验、清洗并标准化输入，再进入核心逻辑；
2. 为当日核心模块补充至少 3 组异常/空值/极值单元测试，并纳入 tests/test_day10.py 回归集合；
3. 捕获可预期异常时，返回结构化错误对象并附带 trace_id，方便在飞书告警群里一眼定位到具体是哪条请求出了岔子。

故障演练二：性能退化、成本突增与线上可观测性盲区（编码不规范导致的 UTF-8 乱码、字典 KeyError 崩溃、API Key 硬编码泄露、HTTP 超时未捕获）

【线上现象】上线试运行两天后，林产品反馈早高峰时段页面转圈变慢，同时财务侧看到大模型 API 账单曲线出现异常毛刺，但翻开服务器日志却只看到零星几句 `print('ok')`，完全无法还原当时到底哪个环节耗时最长、哪条 Prompt 吃掉了最多 Token。

【根因定位】缺少工程化的日志分级、耗时打点与配额熔断机制。很多从零基础转行过来的同学习惯用 `print` 调试完就留在线上，既没有时间戳和请求追踪号，也没有统计输入/输出 Token 数和单步耗时；一旦外部接口抖动或触发死循环重试，成本就会在几分钟内失控。

【止血与根治方案】

1. 严格使用标准 logging 模块替代裸 print，记录关键节点的入参摘要、耗时毫秒数（latency_ms）和状态码；
2. 针对所有外部 I/O（文件、数据库、HTTP/LLM API）显式设置 timeout 超时上限和最大重试次数（通常 <= 3 次 + 指数退避）；
3. 定期对照今日 SLA 基线（单次 CLI 指令响应 < 200ms，API 异常捕获率 100%，单元测试覆盖核心路径）跑压测回归，把隐性瓶颈消灭在灰度发布之前。

故障演练三：国内团队跨环境一致性问题（开发环境能跑，测试/Docker 环境报错）

【线上现象】学员在自己 Windows/Mac 笔记本的 VS Code 里运行 Day 10 代码一切正常，但提交到 GitLab CI（Linux Debian 容器环境）后，出现文件路径分隔符报错、时区偏差或国内网络下载依赖超时。

【根因定位】代码中硬编码了反斜杠路径（如 `data\test.json`）或绝对路径（如 `C:\Users\...`），未统一使用 `pathlib.Path`；同时 `pip install` 未指定国内镜像源或 `requirements.txt` 未锁定主版本号。

【止血与根治方案】

1. 全仓库统一使用 pathlib.Path(__file__).resolve().parent 构建相对路径，彻底告别跨平台路径坑；
2. 打开文本文件强制显式传参 encoding='utf-8'，避免 Windows 默认 GBK 编码引发的 UnicodeDecodeError；
3. 依赖安装统一配置清华源 -i https://pypi.tuna.tsinghua.edu.cn/simple，并在 README.md 中固定 Python 3.11+ 版本要求。

def safe_parse_int(value: object, default: int = 0) -> int:
    """将任意输入安全解析为整数，失败时返回 default。"""

作业 2：企业实战：带最大重试次数的同步重试函数企业实战

编写 retry_call(fn, max_attempts=3)，当 fn() 抛出 TimeoutError 时自动重试，若超过最大次数仍失败则将最后一次异常抛出。

💡 思路提示：循环 `range(1, max_attempts + 1)`，在最后一次迭代直接 `raise`。

✅ 参考实现代码（作业 2）
"""Day 10 课后题 2：指定异常重试执行器。"""

from typing import Callable, TypeVar

T = TypeVar("T")


def retry_call(fn: Callable[[], T], max_attempts: int = 3) -> T:
    """遇到 TimeoutError 时自动重试，最多执行 max_attempts 次。"""
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TimeoutError:
            if attempt == max_attempts:
                raise
    raise RuntimeError("unreachable")


if __name__ == "__main__":
    state = {"count": 0}

    def flaky_api() -> str:
        state["count"] += 1
        if state["count"] < 3:
            raise TimeoutError(f"第 {state['count']} 次超时")
        return "第 3 次调用成功！"

    print(retry_call(flaky_api, max_attempts=3))

作业 3：架构进阶：自定义上下文超长异常与自动截断恢复架构进阶

定义 ContextOverflowError(StarMindError) 携带 max_chars 属性；编写调用包装器，当捕获到该异常时自动将 prompt 截断至 max_chars 后重新调用一次。

💡 思路提示：捕获 `ContextOverflowError as e:` 后用 `prompt[:e.max_chars]` 二次尝试。

✅ 参考实现代码（作业 3）
"""Day 10 课后题 3：上下文超长自愈恢复机制。"""


class ContextOverflowError(Exception):
    def __init__(self, max_chars: int) -> None:
        super().__init__(f"上下文超过最大长度 {max_chars}")
        self.max_chars = max_chars


def invoke_with_auto_truncate(model_fn, prompt: str) -> str:
    try:
        return model_fn(prompt)
    except ContextOverflowError as exc:
        trimmed = prompt[: exc.max_chars]
        return model_fn(trimmed)


if __name__ == "__main__":
    def strict_model(text: str) -> str:
        if len(text) > 10:
            raise ContextOverflowError(max_chars=10)
        return f"OK({text})"

    print(invoke_with_auto_truncate(strict_model, "这是一段超过十个字符的长提问文本"))

异常对象携带业务参数 max_chars，让外层容错逻辑具备「自愈能力」，非常贴近真实 LLM 网关处理超长上下文的做法。
