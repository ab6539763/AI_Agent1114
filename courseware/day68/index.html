3. 架构设计与矢量工程图谱（流程图 / 架构图 / 原理示意图）

3.1 架构设计思路与技术选型权衡

设计 **日活 10 万（100K DAU）企业级知识库与 Agent 平台** 的标准系统设计 5 步法：
1. **容量估算（Back-of-the-Envelope）**：
- 假设 100K DAU，人均日提问 10 次 -> 日请求 100 万次 -> 平均 QPS ≈ 11.6，早高峰（峰值系数 5x）**Peak QPS ≈ 58**。
- 引入 L1 语义缓存（命中率 35%）后，实际穿透至模型层的 **LLM Peak QPS ≈ 38**。
- 若单请求平均输入+输出 2000 tokens，则峰值吞吐约 38 * 2000 = 76,000 tokens/s；结合分级路由（70% 走 7B vLLM，30% 走旗舰云 API）即可精确算出所需 GPU 卡数与月度账单。
- 向量库：1000 万切片 × 1024 维 × FP32（4 Bytes）× HNSW 索引开销系数（1.5x）≈ **61 GB RAM**，采用多租户分区 + 标量量化（SQ8）可压至 ~16 GB。
2. **高可用多租户架构**：接入层限流熔断 -> L1 语义缓存 -> 异步解耦索引流水线（Kafka + 文档解析 Worker 保证分钟级增量更新） -> 多租户 RBAC 前置过滤混合检索 -> 多模型网关（vLLM 主集群 + 云 API 溢流兜底）。

"""
Day 68 - 模块一：十万 DAU 企业级 RAG + Agent 平台系统设计容量与成本估算引擎
"""
from __future__ import annotations

import math
from dataclasses import dataclass


@dataclass
class ScaleSpec:
    dau: int = 100_000
    queries_per_user_day: float = 10.0
    peak_factor: float = 5.0
    cache_hit_rate: float = 0.35
    avg_tokens_per_query: int = 2000
    total_chunks: int = 10_000_000
    embedding_dim: int = 1024
    use_sq8_quant: bool = True
    single_gpu_tps: float = 1500.0  # 单张 A100/L40S 跑 7B vLLM 吞吐估算(tokens/s)
    local_route_ratio: float = 0.70


@dataclass
class CapacityReport:
    daily_requests: int
    avg_qps: float
    peak_qps: float
    llm_peak_qps: float
    vector_ram_gb: float
    required_gpus: int
    monthly_cloud_only_cny: float
    monthly_hybrid_cny: float


def estimate_capacity(spec: ScaleSpec) -> CapacityReport:
    daily_reqs = int(spec.dau * spec.queries_per_user_day)
    avg_qps = daily_reqs / 86400.0
    peak_qps = avg_qps * spec.peak_factor
    llm_peak_qps = peak_qps * (1.0 - spec.cache_hit_rate)

    # 向量内存估算：FP32 为 4 bytes/dim，SQ8 标量量化为 1 byte/dim，HNSW 图索引开销约 1.5x
    bytes_per_dim = 1 if spec.use_sq8_quant else 4
    raw_bytes = spec.total_chunks * spec.embedding_dim * bytes_per_dim * 1.5
    vector_ram_gb = round(raw_bytes / (1024 ** 3), 2)

    # 本地 7B 峰值输出吞吐需求（按总 token 的 30% 为输出 decode token 估算 + 30% 冗余）
    local_peak_decode_tps = llm_peak_qps * spec.local_route_ratio * (spec.avg_tokens_per_query * 0.30)
    required_gpus = max(1, math.ceil((local_peak_decode_tps * 1.3) / max(1.0, spec.single_gpu_tps)))

    # 月度成本对比（云旗舰均价 0.02 元/千Token；单 GPU 月租 6000 元）
    monthly_tokens_k = (daily_reqs * 30 * spec.avg_tokens_per_query) / 1000.0
    cloud_only_cny = round(monthly_tokens_k * 0.02, 2)
    hybrid_cloud_part = monthly_tokens_k * (1.0 - spec.cache_hit_rate) * (1.0 - spec.local_route_ratio) * 0.02
    hybrid_cny = round(hybrid_cloud_part + required_gpus * 6000.0, 2)

    return CapacityReport(
        daily_requests=daily_reqs,
        avg_qps=round(avg_qps, 2),
        peak_qps=round(peak_qps, 2),
        llm_peak_qps=round(llm_peak_qps, 2),
        vector_ram_gb=vector_ram_gb,
        required_gpus=required_gpus,
        monthly_cloud_only_cny=cloud_only_cny,
        monthly_hybrid_cny=hybrid_cny,
    )


if __name__ == "__main__":
    rep = estimate_capacity(ScaleSpec())
    print("十万 DAU 容量估算报告:", rep)

"""
Day 68 - 模块二：应对'项目被问穿'的 5 层架构决策记录 (ADR) 生成与完整度校验器
"""
from __future__ import annotations

from dataclasses import dataclass
from typing import Dict, List


@dataclass
class ArchitectureDecisionCard:
    topic: str
    l1_problem: str
    l2_alternatives: List[str]
    l3_pitfall_lesson: str
    l4_metric_proof: str
    l5_scale_10x_plan: str

    def to_markdown(self) -> str:
        alts = " / ".join(self.l2_alternatives)
        return (
            f"### ADR: {self.topic}\n"
            f"- **L1 痛点与目标**: {self.l1_problem}\n"
            f"- **L2 备选方案权衡**: {alts}\n"
            f"- **L3 真实踩坑与解法**: {self.l3_pitfall_lesson}\n"
            f"- **L4 量化指标实证**: {self.l4_metric_proof}\n"
            f"- **L5 十倍扩容演进**: {self.l5_scale_10x_plan}\n"
        )


def audit_adr_readiness(card: ArchitectureDecisionCard) -> Dict[str, object]:
    missing: List[str] = []
    if len(card.l1_problem.strip()) < 8:
        missing.append("L1 痛点描述过于空泛")
    if len(card.l2_alternatives) < 2:
        missing.append("L2 至少需对比 2 种备选技术方案及其取舍")
    if len(card.l3_pitfall_lesson.strip()) < 8:
        missing.append("L3 缺少真实踩坑排障细节，容易被面试官怀疑是纸上谈兵")
    if not any(ch.isdigit() for ch in card.l4_metric_proof):
        missing.append("L4 缺少量化指标数字支撑")
    if len(card.l5_scale_10x_plan.strip()) < 8:
        missing.append("L5 缺少流量或数据量扩大 10 倍后的演进预案")
    return {"ready": len(missing) == 0, "missing": missing}

很多零基础转行或者刚毕业的同学进公司后，最容易踩的第一个坑不是代码写不出来，而是“需求没听懂就开始埋头写代码”，写完三天提测才发现跟产品经理要的南辕北辙。今天我们以 STARMIND-068（面试专题(二)——项目深挖与系统设计：应对'项目被问穿'与十万 DAU 企业知识库架构）为例，把星辰数科每周一上午需求评审会的真实对话逻辑拆开揉碎了讲给你听。业务背景非常明确：高级 AI 工程师二/三面核心考察两点：一是候选人对自研项目每个架构决策的深度权衡（防问穿）；二是面对十万级 DAU 大规模企业知识库时的容量估算（Back-of-the-Envelope Estimation）与高可用架构设计能力。 在评审会上，林产品抛出来的核心业务痛点集中在：（1）面对面试官连环 5 层追问只记得'用了什么工具'，说不出备选方案对比、真实失败实验与量化依据。；（2）系统设计只会画模糊框图，算不清峰值 QPS、向量内存、GPU 副本数与月度成本。。如果你只盯着字面意思去写一个“一次性脚本”，短期看似交付很快，但两周后业务方加一个新字段、换一个大模型厂商或者并发量翻倍时，整段代码就得推倒重来。

老陈在评审会上通常只追问三个致命问题，建议你拿小本本记下来，以后带项目直接套用：第一问“输入数据的最坏情况长什么样？”——比如用户会不会粘进来 5 万字乱码、空文件、或者带 SQL 注入/提示词注入的恶意文本；第二问“业务方能接受的失败兜底策略是什么？”——在大模型应用里，100% 不出错是不可能的，关键是出错时系统是直接 500 白屏，还是友好提示、自动降级并留存日志；第三问“哪些指标能证明我们今天这版上线是成功的？”——围绕今天定下的交付目标：（1）实现十万级 DAU 企业 RAG + Agent 平台容量与成本估算引擎（峰值 QPS、TPM、向量库 RAM、GPU 卡数与云/自建成本对比）。；（2）实现'防问穿' 5 层项目深挖演练与架构决策记录（ADR: Context/Options/Decision/Tradeoffs/Scale-out）校验器。，必须全部翻译成可量化的测试用例和监控指标（例如 全量单元测试 100% 通过、核心接口 P95 延迟可控、GitHub 作品集与架构文档可直接用于一线大厂面试）。

经过这三轮对齐，我们在飞书需求文档里落定了今天的技术边界：明确哪些能力放在当天版本 versions/day68/ 里做透做稳，哪些属于过度设计（Over-engineering）暂时留好接口扩展位而不急着实现。记住国内互联网大厂一条铁律：好的架构不是一开始就画一张大而全的宇航级图纸，而是像今天这样，在清晰抽象边界的前提下，让每一个迭代版本都能独立跑通、独立测试、独立交付业务价值。

实战方法论三：从“能跑就行”到“生产级代码”——Day 68 模块的代码品味与重构准则

今天我们在 versions/day68/ 中亲手编写了 src/day68_capacity_estimator.py、src/day68_deep_dive_defense.py 以及对应的自动化测试 tests/test_day68.py。站在初级开发者视角，代码只要在控制台打印出预期结果就算大功告成；但站在星辰数科技术委员会的 Code Review 视角，一段代码能不能合入主干，要过四道硬核关卡：第一关是“单一职责与低耦合”——函数长度尽量控制在 40~60 行以内，如果一个函数既负责读取配置、又负责清洗文本、还负责调接口和写文件，那它一定难以复用和单测；第二关是“命名即文档”——变量名绝不用 a、b、data1、temp2，而是直接用业务含义命名（如 sanitized_prompt、chunk_overlap、trace_id），配合 Python 类型注解（Type Hints），让阅读者一眼看清数据契约；第三关是“显式错误处理”——绝不写光秃秃的 except: pass 吞掉异常，因为吞掉异常等于在生产环境埋下一颗定时炸弹，真出故障时连日志都查不到；第四关是“可测试性”——任何涉及外部网络、系统时间、随机数或付费大模型 API 的逻辑，都要支持通过依赖注入或 local_mock 切换在离线环境 100% 确定性地跑通回归测试。

对照这四道关卡回头审视你今天写下的每一行代码，你会清晰感受到：大模型应用开发绝不是“调个 API 写两句提示词”那么肤浅的玩具活，它本质上是“扎实的软件工程底座 + 大模型概率特性治理 + 垂直业务场景洞察”的三位一体。国内企业现在最缺、薪资给得最高的，恰恰是既懂 Python/FastAPI/Docker 工程落地，又懂 RAG/Agent/微调底层调优的复合型 AI 应用工程师。

9. 生产环境排障实录与工程验收自查表

故障演练一：面试专题(二)——项目深挖与系统设计：应对'项目被问穿'与十万 DAU 企业知识库架构 核心链路在异常脏数据或边界输入下触发未预期中断

【线上现象】在联调 STARMIND-068 对应的功能模块时，开发机上用自己构造的“干净样例”跑得丝滑无比，但一交给阿杰跑边界测试（如空文本、超长中文混排、包含特殊 Emoji 或嵌套缺失字段的 JSON），控制台直接抛出未捕获异常，导致整个服务进程或上游调用链雪崩。

【根因定位】根本原因在于把“理想假设”当成了“生产契约”。在 全栈架构整合、全链路自动化测试与压测、生产部署上线、技术答辩与 STAR 简历打磨、高频八股与日活十万级系统设计 环节，上游业务系统传过来的数据往往充满历史包袱（比如字段值为 None 而非空字符串、编码混杂 GBK/UTF-8、或者模型偶发少输出一个右括号）。如果函数入口缺少显式的参数防御与 Pydantic/类型校验，异常就会在深层调用栈里爆炸。

【止血与根治方案】

1. 在所有对外暴露的入口函数与接口层建立“防御性边界”，先校验、清洗并标准化输入，再进入核心逻辑；
2. 为当日核心模块补充至少 3 组异常/空值/极值单元测试，并纳入 tests/test_day68.py 回归集合；
3. 捕获可预期异常时，返回结构化错误对象并附带 trace_id，方便在飞书告警群里一眼定位到具体是哪条请求出了岔子。

故障演练二：性能退化、成本突增与线上可观测性盲区（模块联调接口契约不一致、上线前缺乏端到端回归测试、面试中对项目指标和踩坑细节讲不清楚）

【线上现象】上线试运行两天后，林产品反馈早高峰时段页面转圈变慢，同时财务侧看到大模型 API 账单曲线出现异常毛刺，但翻开服务器日志却只看到零星几句 `print('ok')`，完全无法还原当时到底哪个环节耗时最长、哪条 Prompt 吃掉了最多 Token。

【根因定位】缺少工程化的日志分级、耗时打点与配额熔断机制。很多从零基础转行过来的同学习惯用 `print` 调试完就留在线上，既没有时间戳和请求追踪号，也没有统计输入/输出 Token 数和单步耗时；一旦外部接口抖动或触发死循环重试，成本就会在几分钟内失控。

【止血与根治方案】

1. 严格使用标准 logging 模块替代裸 print，记录关键节点的入参摘要、耗时毫秒数（latency_ms）和状态码；
2. 针对所有外部 I/O（文件、数据库、HTTP/LLM API）显式设置 timeout 超时上限和最大重试次数（通常 <= 3 次 + 指数退避）；
3. 定期对照今日 SLA 基线（全量单元测试 100% 通过、核心接口 P95 延迟可控、GitHub 作品集与架构文档可直接用于一线大厂面试）跑压测回归，把隐性瓶颈消灭在灰度发布之前。

故障演练三：国内团队跨环境一致性问题（开发环境能跑，测试/Docker 环境报错）

【线上现象】学员在自己 Windows/Mac 笔记本的 VS Code 里运行 Day 68 代码一切正常，但提交到 GitLab CI（Linux Debian 容器环境）后，出现文件路径分隔符报错、时区偏差或国内网络下载依赖超时。

【根因定位】代码中硬编码了反斜杠路径（如 `data\test.json`）或绝对路径（如 `C:\Users\...`），未统一使用 `pathlib.Path`；同时 `pip install` 未指定国内镜像源或 `requirements.txt` 未锁定主版本号。

import math


def recommend_shards(total_chunks: int, max_per_shard: int = 2_000_000) -> int:
    return max(1, math.ceil(total_chunks / max_per_shard))

def find_spof(replicas: dict[str, int]) -> list[str]:
    return [k for k, v in replicas.items() if v < 2]
